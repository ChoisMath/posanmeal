# 학년도별 학생·교사 명부 — 요구사항 인계 (2026-09-19)

## 진행 상태

사용자가 “좋습니다. 이대로 구현 계획을 작성해 주세요.”라고 승인하여 [상세설계 spec](../../docs/superpowers/specs/2026-09-19-academic-year-roster-design.md) 전체와 §13 세부정책의 합의를 완료했다. [15 Tasks 구현계획](../../docs/superpowers/plans/2026-09-19-academic-year-roster.md) 작성과 주 작업자 자체 검토를 마쳤으며, 현재 사용자 계획 검토와 실행방식(Subagent-driven 권장 / Native) 선택 대기다. 앱 구현은 시작하지 않았다. 상세설계의 이전 로컬 커밋은 `04edcc0`이며 이번 계획은 아직 미커밋이다.

## 사용자 확정사항

- 현재 모든 명부·식사·체크인은 2026학년도 자료이며 앞으로 학년도별로 누적한다. 학년도는 KST 3월 1일부터 다음 해 2월 말일까지다.
- 기존 `User.id`를 유지하는 추가형 학년도 정보 도입을 승인했다. 이메일은 재학 중 동일하게 유지하고 예외 변경은 관리자가 처리한다.
- 과거 식사·체크인은 해당 학년도의 최종 학급으로 표시한다. 다운로드에서는 현재 학급 병기를 선택할 수 있다. 연중 학년·반·번호 수정은 해당 학년도 전체 표시를 바꾸며 날짜별 반 이력은 관리하지 않는다.
- 과거 명부 삭제를 허용하되 내역 표시용 당시 학급은 계속 보존한다. 명부를 숨기기만 하는 방식으로 합의된 것은 아니다. 구체적인 삭제·보존 구조는 상세설계 대상이다.
- 졸업·전출자는 로그인을 차단하고 사용자 및 기록은 보존해 관리자가 조회한다.
- 새 학년도 명부는 미리 초안으로 업로드·검토한 뒤 관리자가 명시적으로 전환한다. 새 학년도 식사 신청은 전환 후에만 허용한다.
- 새 명부에서 누락된 학생은 별도 목록으로 표시하고 관리자가 졸업·전출·보완을 처리한다. 3학년은 졸업 후보로만 자동 표시하며 자동 졸업 처리하지 않는다.
- 단일 `.xlsx` 안의 `[학생]`, `[교사]` 시트를 함께 업로드한다. 두 시트 모두 A열은 `email`이다. 학생 열은 `email / 학년 / 반 / 번호 / 이름 / 성별`, 교사 열은 `email / 이름 / 교과 / 담임학급 / 직위`다.
- 다운로드는 양식만 받기와 기존 자료 포함을 선택한다.
- 교사 업무 정보는 학년도별로 관리한다. `adminLevel`은 메인 관리자가 별도로 지정하며 Excel로 변경하지 않는다.
- spec §13의 Excel 반영·충돌 정책, 교사 누락과 이용 중단, 메인 관리자 전환·삭제 권한, 교사 본인 업무 수정 종료, 공고 연도 경계, 로컬 명부 유효기간·재동기화, 삭제 명부 다운로드 종료도 승인됐다. 세부 규칙은 승인된 spec을 기준으로 한다.

## 읽기 전용 조사 결과

아래는 주 작업자가 이번 세션에 코드·설정을 조사해 전달한 결과다. 이 인계 문서 작성 과정에서 앱 코드를 재조사하거나 DB 상태를 확인한 것은 아니다.

- `User.email`은 unique이며 관계는 `userId`를 사용한다. `User` 삭제는 신청·체크인·얼굴 자료에 Cascade 영향을 준다. 학년도 모델은 아직 없다.
- 기존 Sheet 가져오기는 이미 email 기반 upsert를 사용한다. 과거 조회는 현재 `User` 필드를 사용하며, `meal-plan-server`의 과거 신청 resync도 현재 grade를 사용한다. 기존 신청 Excel 가져오기는 현재 학년·반·번호로 매칭한다.
- 인증 권한은 로그인 시 JWT에 복사하며 기존 세션 권한을 무효화하는 처리는 없다. 현재 교사는 자신의 homeroom을 수정할 수 있다.
- `railway.json` 시작 명령에 `migrate deploy`가 포함된다. 현재 운영 인프라 연결을 확인하거나 배포한 결과는 아니다.

## 수행·검증 범위

- 이번 작업은 승인된 상세설계를 바탕으로 구현계획을 작성하고 이 문서·`MEMORY.md`의 인계를 갱신한 것이다. 앱 코드·Prisma 스키마·DB·legacy·전역 메모리는 변경하지 않았다.
- 인계 갱신 시 프로젝트 지침·역할 지침·프로젝트 맵·메모리 색인·탐색 규칙과 기존 변경 상태를 확인했다.
- 주 작업자 전달 기준으로 문서 경로·수정 대상 파일 존재·15개 Task·미정 문구 검사, TypeScript 코드 블록 29개 문법 검사(오류 0)와 기존 추적 파일 `git diff --check`를 통과했다. 예시 문법 검사는 앱 타입 검사나 테스트 실행을 뜻하지 않는다. 새 계획의 `git diff --no-index --check`는 공백 오류 출력 없이 차이 존재로 exit 1이었다.
- 인계의 spec/plan 상대경로는 `.codex/memory/` 기준 `../../docs/`가 올바르며 대상 존재로 확인했다. 인계 담당자는 두 파일의 상대링크 대상 존재·옛 승인 대기 문구 제거·`git diff --check`를 직접 확인했다.
- `prisma-migration-guardian` 개념 검토를 완료하고 지연 동기화의 근거와 교사 자격 구분, 공통 잠금과 DB의 ACTIVE 유일 제약, 초기 귀속 예외 시 전환 차단, 완료 후 삭제한 명부의 backfill 재생성 금지를 설계에 반영했다. 실제 migration SQL 승인이나 운영 데이터 보존 검증은 아니다.
- 주 작업자 전달 기준으로 실제 기존 자료·비밀값·학생 데이터 열람 및 DB 접속은 없었다. 앱 테스트·타입 검사·빌드·DB 복원·마이그레이션·배포는 실행하지 않았다.

## 미완료 및 다음 단계

1. 사용자 계획 검토와 실행방식 선택 후 구현한다. Task 1~3 격리 테스트·추가형 모델/제약·2026 초기 이전 → 4~9 계정/권한·명부·Excel·전환·삭제 → 10~14 신청/과거 조회·온라인/로컬 동기화·UI → 15 전체 회귀·복원 리허설·운영 실행안 순서다. 작업 간 의존성은 계획 표를 따른다.
2. 운영 DB에 변경을 적용하기 전에 실제 migration SQL을 검토하고, 운영과 분리된 DB 및 사진/Volume 복사본으로 실제 복원을 검증한다. 복원본에서 이전 전후 원본 전체 필드·PK/FK 비교와 전환·신청·온라인/오프라인 검증을 마친다. 백업 파일 생성이나 합성 테스트만으로 복원 검증 완료라고 판단하지 않는다.
3. 전환 원자성·기존 세션 차단·오프라인 동기화 등은 계획만 수립됐으며 구현·실행 검증은 미완료다. 운영 서비스 생성·운영 반영은 대상·비용·실행 순서를 구체화한 별도 절차로 처리한다. 이번 계획의 로컬 커밋 완료 여부는 후속 기록하며, 이 인계는 push·배포 완료를 의미하지 않는다.

## 2026-09-19 계획 검토 뒤 개정 (Claude Code 세션)

spec과 계획을 코드와 대조해 검토하고, 사용자와 질의응답으로 아래를 확정해 두 문서에 반영했다(spec §13의 8~14, 계획 "계획 자체 검토 기록"의 개정 항목). 문서만 수정했으며 앱 코드·스키마·DB·배포는 건드리지 않았고 테스트·빌드도 실행하지 않았다.

- 로컬 명부: 자정 하드 차단 폐기. 자정 뒤에도 내려받은 자격(오늘~13일)으로 체크인 허용 + `재동기화 필요` 표시. 운영 학년도 불일치·명부 없음·자격 범위 밖일 때만 차단. **Why:** 동기화에 관리자 로그인이 필요해 아침 네트워크 장애 시 로컬 모드가 통째로 멈춘다.
- 이용 중단(졸업·전출·퇴직)과 같은 트랜잭션에서 `FaceProfile` 삭제. **Why:** `face-consent.ts` 보유 기간이 "졸업·전출 또는 본인 삭제 요청 시까지".
- 오래된 Excel: 바뀐 행만 `CONFLICT`, 행별 파일 값/서버 값 선택. 파일 전체 거절 없음.
- 3월 1일 이전 전환 허용 + 경고 3종(이용 중단자의 미래 확정 식사일, 현 학년도 잔여 확정 식사일, 전년도와 학년이 같은 학생 수)과 메인 관리자 확인.
- 배포 2단계: Release A = Task 1~4A(스키마·백필·세션 버전·호환 쓰기, 기존 쓰기 비차단, 전원 1회 재로그인), Release B = Task 5~14. `PREPARING`은 새 기능만 막는다.
- 명부 사본 보존: 업로드 입력·미리보기는 확정/취소 즉시(미확정 24시간), 대응표·키오스크 근거 30일, 이전 명부 삭제 시 동반 삭제. 정리는 요청 처리 끝에 기회적으로 실행.
- 잠금: 전환·Excel 확정만 전역 배타. 셀 편집·계정 변경은 control 공유 잠금 + 사용자 행 버전(`withUserMutation`), 신청·공고는 공고 행 잠금, 체크인은 잠금 없음. 전역 트랜잭션은 일괄 쓰기 + `{maxWait:10s, timeout:60s}`. `eligibilityVersion` 카운터는 `EligibilityEvent.id`(sequence)로 대체.
- 검토 기록 종결: 재송신 시 현재 상태 반환, `final=true`면 로컬 정리, Excel 내보내기 후 강제 초기화 허용. IDB 실브라우저 검증은 v4·v5→v6만.
- 9월 19일 반영된 `/facecheck` 2단계 확인 흐름과 `KioskViewport`를 Task 12·13의 전제로 명시했다.
- `.claude/PROJECT_MAP.md`를 `.codex/PROJECT_MAP.md` 기준으로 동기화했다(§13 관리 규칙만 서로 다름). Railway 연결은 6월·9월 기록이 달라 여전히 미확인이며 GitHub Actions는 없다.
