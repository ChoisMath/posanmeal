# 학년도별 학생·교사 명부 — 요구사항 인계 (2026-09-19)

## 진행 상태

요구사항 합의와 읽기 전용 코드 조사를 바탕으로 [상세설계 spec](../../docs/superpowers/specs/2026-09-19-academic-year-roster-design.md)을 작성했다. 현재 사용자 문서 검토 대기이며, 구현계획·앱 구현은 진행 전이다. 아래 확정사항과 spec §13의 새 세부 제안을 구분한다. §13은 아직 사용자 합의가 아니다.

## 사용자 확정사항

- 현재 모든 명부·식사·체크인은 2026학년도 자료이며 앞으로 학년도별로 누적한다. 학년도는 KST 3월 1일부터 다음 해 2월 말일까지다.
- 기존 `User.id`를 유지하는 추가형 학년도 정보 도입을 승인했다. 이메일은 재학 중 동일하게 유지하고 예외 변경은 관리자가 처리한다.
- 과거 식사·체크인은 해당 학년도의 최종 학급으로 표시한다. 다운로드에서는 현재 학급 병기를 선택할 수 있다. 연중 학년·반·번호 수정은 해당 학년도 전체 표시를 바꾸며 날짜별 반 이력은 관리하지 않는다.
- 과거 명부 삭제를 허용하되 내역 표시용 당시 학급은 계속 보존한다. 명부를 숨기기만 하는 방식으로 합의된 것은 아니다. 구체적인 삭제·보존 구조는 상세설계 대상이다.
- 졸업·전출자는 로그인을 차단하고 사용자 및 기록은 보존해 관리자가 조회한다.
- 새 학년도 명부는 미리 초안으로 업로드·검토한 뒤 관리자가 명시적으로 전환한다. 새 학년도 식사 신청은 전환 후에만 허용한다.
- 새 명부에서 누락된 학생은 별도 목록으로 표시하고 관리자가 졸업·전출·보완을 처리한다. 3학년은 졸업 후보로만 자동 표시하며 자동 졸업 처리하지 않는다.
- 단일 `.xlsx` 안의 `[학생]`, `[교사]` 시트를 함께 업로드한다. 두 시트 모두 A열은 `email`이다. 학생 열은 `email / 학년 / 반 / 번호 / 이름 / 성별`, 교사 열은 `email / 이름 / 교과 / 담임학급 / 직위`다.
- 다운로드는 양식만 받기와 기존 자료 포함을 선택한다.
- 교사 업무 정보는 학년도별로 관리한다. `adminLevel`은 메인 관리자가 별도로 지정하며 Excel로 변경하지 않는다.

## 읽기 전용 조사 결과

아래는 주 작업자가 이번 세션에 코드·설정을 조사해 전달한 결과다. 이 인계 문서 작성 과정에서 앱 코드를 재조사하거나 DB 상태를 확인한 것은 아니다.

- `User.email`은 unique이며 관계는 `userId`를 사용한다. `User` 삭제는 신청·체크인·얼굴 자료에 Cascade 영향을 준다. 학년도 모델은 아직 없다.
- 기존 Sheet 가져오기는 이미 email 기반 upsert를 사용한다. 과거 조회는 현재 `User` 필드를 사용하며, `meal-plan-server`의 과거 신청 resync도 현재 grade를 사용한다. 기존 신청 Excel 가져오기는 현재 학년·반·번호로 매칭한다.
- 인증 권한은 로그인 시 JWT에 복사하며 기존 세션 권한을 무효화하는 처리는 없다. 현재 교사는 자신의 homeroom을 수정할 수 있다.
- `railway.json` 시작 명령에 `migrate deploy`가 포함된다. 현재 운영 인프라 연결을 확인하거나 배포한 결과는 아니다.

## 수행·검증 범위

- 이번 작업은 상세설계 spec 작성과 이 문서·`MEMORY.md` 인계 갱신이다. 앱 코드·Prisma 스키마·DB·legacy·전역 메모리는 변경하지 않았다.
- 인계 갱신 시 프로젝트 지침·역할 지침·프로젝트 맵·메모리 색인·탐색 규칙과 기존 변경 상태를 확인했다.
- 주 작업자는 문서 경로·placeholder 검사와 `git diff --check`를 실행해 통과했다. 인계 갱신 후 연결 경로와 공백 오류도 확인했다.
- `prisma-migration-guardian` 개념 검토를 완료하고 지연 동기화의 근거와 교사 자격 구분, 공통 잠금과 DB의 ACTIVE 유일 제약, 초기 귀속 예외 시 전환 차단, 완료 후 삭제한 명부의 backfill 재생성 금지를 설계에 반영했다. 실제 migration SQL 승인이나 운영 데이터 보존 검증은 아니다.
- 주 작업자 전달 기준으로 실제 기존 자료·비밀값·학생 데이터 열람 및 DB 접속은 없었다. 앱 테스트·타입 검사·빌드·마이그레이션·배포는 실행하지 않았다.

## 미완료 및 다음 단계

1. 작성된 상세설계 spec의 사용자 승인을 받는다. 특히 §13의 Excel 반영·충돌 정책, 교사 누락과 이용 중단, 메인 관리자 전환·삭제 권한, 교사 본인 업무 수정 종료, 공고 연도 경계, 로컬 명부 유효기간·재동기화, 삭제 명부 다운로드 종료는 새 제안으로 검토받는다.
2. 문서 승인 후 구현계획을 작성하고, 계획 검토 후 구현한다. 전환 원자성·별도 DB 복원·기존 세션 차단·오프라인 동기화는 설계만 작성했으며 실제 구현·검증은 미완료다.
3. 문서만 로컬 커밋할 예정이며 push는 하지 않는다. 이 기록은 커밋 완료를 의미하지 않는다.
