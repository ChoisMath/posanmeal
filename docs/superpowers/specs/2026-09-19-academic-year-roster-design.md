# 학년도별 사용자 관리와 Excel 명부 전환 설계

- 작성일: 2026-09-19
- 상태: 사용자 검토 대기. 요구사항과 추가형 구조는 합의했으며, 아래 상세 동작은 이 문서의 검토 대상이다.
- 범위: 관리자 사용자 관리, 학년도 전환, 학생·교사 명부, 관련 식사 조회·신청·인증·키오스크의 연도 일관성
- 구현 상태: 설계 문서만 작성. 앱 코드, Prisma 스키마, 실제 DB, 배포환경은 변경하지 않았다.
- 요구사항 근거: `../../../.codex/memory/2026-09-19-academic-year-roster-requirements.md`

## 1. 목표와 보존 기준

학생과 교사를 이메일로 찾아 같은 사용자로 유지하면서, 학년·반·번호와 교과·담임·직위는 학년도별로 관리한다. 관리자는 하나의 Excel 파일로 명부를 준비하고, 변경 미리보기를 확인한 뒤 반영한다. 새 학년도는 준비 상태에서 별도로 관리하다가 명시적인 전환으로 운영에 적용한다.

성공 기준은 다음과 같다.

1. 기존 `User.id`와 식사 신청·확정일·체크인·얼굴 등록·사진 연결이 유지된다.
2. 2027학년도 전환 뒤에도 2026학년도 식사 내역은 2026학년도 최종 학급으로 표시된다.
3. 같은 학년도의 학급 정정은 그 학년도 전체 표시를 바꾸며, 다른 학년도에는 영향을 주지 않는다.
4. 명부 삭제가 사용자 삭제나 식사 기록 삭제로 이어지지 않는다.
5. 새 학년도 초안을 업로드해도 현재 운영 정보와 접수·체크인은 변하지 않는다.
6. 파일 오류나 저장 실패 때문에 학생 또는 교사 일부만 반영되지 않는다.
7. 기존 데이터 이전은 별도 DB에서 검증하고, 운영 반영 전후의 원본 보존을 비교한다.

| 변경 방식 | 기존 구조에 학년도 정보를 추가하고 기능을 단계적으로 전환 |

## 3. 현재 코드에서 확인한 변경 이유

- `prisma/schema.prisma`의 `User.id`가 영구 키이고 `email`은 unique다. 신청·체크인·얼굴 등록은 `userId`로 연결된다. 현재 `User` 삭제는 종속 자료를 Cascade 삭제한다.
- 학생 소속과 교사 업무는 `User`의 현재값뿐이며 학년도 정보가 없다.
- `src/app/api/admin/import/route.ts`는 이미 이메일 upsert를 사용하지만 미리보기·전체 파일 단위 원자 반영이 없다.
- 관리자 체크인·내보내기, 담임 조회는 과거 자료에도 현재 `User` 소속을 사용한다.
- `src/lib/meal-plan-server.ts`의 재동기화는 현재 학년을 사용하므로 진급 뒤 과거 공고를 수정하면 과거 확정일이 바뀔 수 있다.
- 기존 식사 신청 Excel은 현재 학년·반·번호로 학생을 찾는다.
- `src/auth.ts`는 로그인 시 권한을 JWT에 넣고 기존 세션의 권한·이용 상태를 재검증하지 않는다.
- `src/app/api/users/me/route.ts`에서 교사가 자신의 담임 등을 수정할 수 있다. 연도별 관리자 명부와 권한 기준을 일치시키려면 이 우회 경로도 정리해야 한다.
- `railway.json`은 앱 시작 시 `prisma migrate deploy`를 실행한다. migration 파일을 포함한 배포 자체가 DB 변경을 일으킬 수 있다.

이 내용은 코드 조사 결과이며 실제 운영 DB의 행·인프라 연결을 확인한 결과가 아니다.

## 4. 데이터 책임과 제안 모델

새 이름과 세부 컬럼은 구현 계획에서 확정하되 다음 책임은 유지한다.

| 단위 | 책임·필수 정보 | 보존 원칙 |
|---|---|---|
| `User` | 기존 ID·이메일·계정 종류·사진·얼굴 연결·관리자 권한, 추가 이용 상태와 세션 버전 | 사용자 관리에서 물리 삭제하지 않음 |
| `AcademicYear` | 연도, `DRAFT / ACTIVE / ARCHIVED`, 변경 버전·전환 시각 | 운영 중 연도는 최대 하나. 달력 날짜만으로 자동 전환하지 않음 |
| `RosterEntry` | 학년도 명부의 항목. 준비 중에는 기존 사용자 연결 또는 신규 이메일과 입력값을 보관 | 이전 명부 삭제의 직접 대상 |
| `UserAcademicRecord` | 사용자·학년도·학생/교사 구분, 이름, 학생 성별·학급 또는 교사업무, 재학/재직·종료 구분 | 해당 학년도 내역 표시의 기준. 명부 삭제 후에도 유지 |
| 가져오기 작업 기록 | 파일 식별자·대상 학년도·기준 버전·정규화 입력·미리보기·확정 결과 | 중복 저장과 오래된 파일 덮어쓰기 방지 |
| 관리 작업 기록 | 작업자·학년도·변경 종류·대상 ID·시각·이용 상태 변경 시각·처리 결과 | 명부 변경·이메일 변경·전환·이용 중단을 추적 |
| 동기화 판정 근거 | 서버가 발급한 동기화 버전, 해당 날짜의 학생 자격·교사 재직 정보, 발급 시각 | 늦게 도착한 체크인을 현재 명부만으로 판정하지 않음 |

### 4.1 한 곳을 기준으로 읽고 쓰기

- 준비 중 입력의 기준은 `RosterEntry`다. 아직 확정하지 않은 신규 사용자를 로그인 가능한 `User`로 만들지 않는다.
- 전환 시 입력을 검증하여 `UserAcademicRecord`를 만들고 기존 또는 신규 `User`와 연결한다.
- 전환 후 소속·업무의 기준은 `UserAcademicRecord` 하나다. `RosterEntry`는 명부 구성원을 나타내며 준비용 입력 사본은 정리한다.
- 기존 `User.grade/classNum/number/subject/homeroom/position` 등은 점진 전환 동안 현재 운영 연도의 호환용 값으로 유지한다. 독립적으로 수정하지 않는다.
- 현재 연도 수정은 연도 기록과 `User` 호환 필드를 같은 트랜잭션으로 바꾼다. 과거 연도 정정은 현재 연도나 현재 로그인 프로필을 바꾸지 않는다.
- 이미 만들어 둔 다음 연도 초안은 현재 연도 수정으로 자동 덮어쓰지 않는다. 이메일·계정 상태 등 준비 이후 바뀐 사항은 전환 전에 다시 검증한다.

### 4.2 필수 제약

- `UserAcademicRecord`는 `(userId, academicYear)`당 하나다.
- 동일 연도 명부에서 연결된 사용자와 정규화한 이메일은 각각 중복될 수 없다. 학생·교사 시트를 통틀어 검사한다.
- 같은 연도 재학 중 명부에서 학년·반·번호는 중복될 수 없다. 전출자 등의 과거 행은 사용자 ID로 구별해 보존한다.
- 학생과 교사의 계정 종류를 Excel 시트 이동으로 자동 변경하거나, 이메일이 비슷하다는 이유로 계정을 합치지 않는다.
- 새 보존 기록에는 명부 삭제를 따라가는 Cascade를 두지 않는다.
- ACTIVE 학년도 최대 1개는 DB 제약으로도 보장한다. 전환·Excel 확정·개별 편집·이메일 변경·이용 중단은 같은 학년도/사용자 버전 및 잠금 규칙에 참여한다. 검사와 쓰기 사이에 다른 수정이 끼어들면 한쪽 작업을 충돌로 종료한다.
- 기존 이메일을 일괄 소문자 변경하지 않는다. 공백 제거·대소문자 비교로 생기는 기존 충돌을 먼저 보고하고, 모호하면 확정을 차단한다. Gmail 점·별칭 제거 같은 추측성 병합은 하지 않는다.

## 5. 관리자 화면

기존 사용자 관리 탭의 학생·교사 구분과 셀 편집을 재사용한다. 상단에 학년도 선택과 `운영 중 / 준비 중 / 이전 학년도` 상태를 표시한다.

주요 동작은 `Excel 다운로드`, `Excel 업로드`, `새 학년도 준비`, `누락자 확인`, `학년도 전환`이다. 이전 학년도에는 명부 다운로드·정정·삭제를 제공하고, 운영 중 명부의 전체 삭제는 제공하지 않는다.

- 현재 연도: 개별 추가·편집 또는 Excel 확인 후 반영.
- 준비 중 연도: 명부를 반복 수정할 수 있으나 현재 서비스에는 미반영.
- 이전 연도: 최종 명부와 기록 확인. 정정은 그 학년도 내역 표시에도 적용됨을 안내.
- 졸업·전출·퇴직 사용자는 계정 삭제 대신 상태로 구별한다.
- 표의 날짜는 식사일이고, 선택 학년도와 실제 달력 연도를 혼동하지 않게 표시한다.
- 기존 반응형 규칙에 따라 표 가로 스크롤, 고정 헤더, 셀 줄바꿈 방지를 유지한다.

## 6. Excel 양식·검증·반영

### 6.1 눈에 보이는 데이터 시트

| 시트 | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| 학생 | 이메일 | 학년 | 반 | 번호 | 이름 | 성별 |
| 교사 | 이메일 | 이름 | 담당교과 | 담임학급 | 직위 | 사용하지 않음 |

다운로드에서 `[✓] 기존 데이터 포함`을 선택한다. 해제하면 안내와 헤더만 받는다. 현재·이전 연도는 선택한 연도 자료를 사용한다. 새 연도 초안에서는 현재 입력값을 받으며, 최초 준비 시 이전 연도 자료를 불러올 수 있다. 이때 학년·반·번호는 자동 진급하지 않고 관리자가 새 배정을 입력한다.

파일에는 대상 학년도·양식 버전·내보내기 식별자를 넣는다. 기존 데이터 행에는 행 순서와 무관한 사용자 대응 정보를 숨김 메타데이터로 보관한다. 보이는 데이터 시트는 학생·교사 둘이며, 메타데이터는 계정 변경 권한으로 신뢰하지 않고 서버의 원본 대응과 대조한다. 기존 데이터 포함 파일의 학년도를 잘못 선택하면 조용히 다른 연도에 반영하지 않는다.

과거 명부 다운로드에는 현재 학급 병기를 선택할 수 있다. 추가되는 현재 학급 열은 참고용이며 업로드 변경값으로 사용하지 않는다.

### 6.2 미리보기

`대상 학년도·반영 범위 선택 → 파일 업로드 → 전체 검증 → 변경 미리보기 → 관리자 확정` 순서다.

- 반영 범위는 `일부 사용자 수정`과 `전체 명부 대조`를 명시한다. 기본은 일부 수정이며 새 학년도 최종 전환 전에는 전체 명부 대조를 완료해야 한다.
- 미리보기는 `신규 / 동일 / 변경 / 확인 필요`로 나누고 변경 전후 값과 시트·행·열 오류를 보여준다.
- 일부 수정에서 파일에 없는 사용자는 변경하지 않는다. 전체 대조의 누락은 확인 목록으로만 보내며 자동 삭제·졸업 처리하지 않는다.
- 두 표준 시트가 필요하다. 헤더만 있는 빈 시트는 해당 역할 변경 없음이며, 전원 삭제나 전원 누락 확정으로 해석하지 않는다.
- 완전히 빈 행은 무시하되 데이터가 있는 행의 이메일·필수값 누락은 오류다.
- 학생은 이메일·이름·학년·반·번호·성별 필수. 학년은 1~3의 정수, 반·번호는 양의 정수. 성별은 기존 `normalizeGender`를 재사용한다.
- 교사는 이메일·이름 필수. 담임학급 빈칸은 비담임이며 기존값 삭제에 해당하면 미리보기에 명확히 표시한다. 교과·직위 빈칸도 값 비우기로 처리한다. 양식에 없는 교사 성별은 변경하지 않는다.
- 파일 내부 및 대상 명부의 이메일·학생 학번 중복, 학생/교사 계정 불일치, 잘못된 담임 표기를 차단한다. 담임학급은 기존 `학년-반` 형식을 검증하며 유효하지 않은 문자열을 권한 기준으로 사용하지 않는다.
- 수식 셀을 계산 결과로 신뢰하지 않는다. 수식 입력은 오류로 표시하고 값으로 입력하도록 안내한다. 기존 파일 크기 제한과 ExcelJS를 재사용한다.
- 기존 행의 이메일을 바꾼 파일은 별도 이메일 변경 절차로 안내한다. 원본 대응 없는 미등록 이메일도 자동 저장하지 않고 신규 대상으로 표시하여 확인받는다.
- 메인 관리자 권한 열은 양식에 없으며, 임의로 추가해도 권한 변경에 사용하지 않는다.

### 6.3 확정과 충돌

- 검증 오류가 남아 있으면 반영하지 않는다. 학생·교사를 하나의 작업으로 저장하고 중간 실패 시 전부 취소한다.
- 확정 직전에 대상 연도·계정·명부 버전을 재검증한다. 미리보기 이후 다른 관리자가 수정했다면 다시 미리보기를 보게 한다.
- 내보낸 뒤 서버에서 값이 바뀐 기존자료 파일은 그대로 덮어쓰지 않고 충돌을 표시한다.
- 같은 확정 요청을 재전송하면 최초 결과를 반환한다. 신규 계정·명부·이력이 중복 생성되지 않는다.
- 현재 연도에 대한 반영과 초안 저장은 화면과 API 모두 구분한다. 초안 저장은 이름·성별을 포함한 기존 `User` 값을 변경하지 않는다.
- 기존 Sheet 가져오기 UI와 서버 쓰기 경로는 새 기능 전환 시 함께 종료한다. 옛 API가 연도 정보를 우회해 현재값만 덮어쓰지 못하게 한다. Google Sheet 원본 및 `code.gs`의 기존 자료는 실행·수정·삭제하지 않는다.

## 7. 학년도 전환

예: `2027학년도 준비 → Excel 편집·검토 → 누락자 처리 → 전환 미리보기 → 전환 실행`.

1. 새 연도의 기간은 고정 규칙으로 계산하지만 전환은 관리자가 실행한다. 3월 1일이 됐다는 이유만으로 자동 변경하지 않는다.
2. 준비 중에는 새 학생 로그인, 새 교사 업무 권한, 해당 연도 급식 접수가 활성화되지 않는다. 공고 작성·임시 준비와 실제 접수는 구분한다.
3. 전체 명부 대조 후 학생 누락은 졸업·전출·보완으로 확인한다. 교사 누락도 전출·퇴직·보완으로 명시적으로 처리하는 방식을 제안한다. 누락·중복·충돌이 남으면 전환할 수 없다.
4. 전환 미리보기에는 사용자 수, 신규 인원, 학급·업무 변경, 이용 중단 대상, 변경하지 않는 관리자 권한을 표시한다. 졸업·전출 처리 시 로그인 차단이 적용됨을 안내한다.
5. 현재 연도와 초안의 버전을 고정해 검증하고, 연도 기록 생성·사용자 현행값 반영·이용 상태·활성 연도·작업 결과를 하나의 트랜잭션으로 저장한다. 실패 시 기존 운영 연도를 유지한다.
6. 완료 뒤에 새 운영 연도의 신청을 받는다. 초안을 대상으로 한 학생·관리자 대리 신청과 신청 Excel 등록도 차단한다.
7. 달력상의 식사 학년도와 운영 중인 명부 연도는 별개다. 전환을 먼저 실행했어도 기존 확정 식사일과 체크인의 소속 연도를 바꾸지 않는다. 전환 시점의 이용 중단은 별도로 적용한다.
8. 전환 자체로 과거 신청 확정일을 재생성하거나 취소하지 않는다. 전환은 되돌리기 버튼으로 식사 원본을 덮어쓰는 기능을 포함하지 않으며, 오류는 명부 정정으로 해결한다.

## 8. 과거 조회·명부 삭제·식사 처리

### 8.1 조회 기준

- 체크인은 KST 식사 날짜로 학년도를 결정하고 그 연도의 `UserAcademicRecord`를 읽는다.
- 공고에는 학년도 참조를 추가한다. 새 공고는 대상 식사일이 한 학년도 안에 있어야 하며 경계를 넘으면 두 공고로 나누도록 안내하는 것을 제안한다.
- 신청 명단·통계·신청 Excel은 공고의 학년도를 사용한다. 기존 신청 Excel 매칭도 이메일과 해당 학년도 사용자 정보를 기준으로 전환한다. 기존 양식은 학년도 내 유일한 학번으로만 확인하고 모호하면 거절한다.
- 전환 후 과거 공고를 수정하더라도 현재 학년으로 과거 신청을 계산하지 않는다. 명부 수정만으로 신청을 다시 계산하지 않으며 공고의 개설일 등을 명시적으로 수정할 때는 해당 연도 학년을 사용한다.
- 같은 연도 학급 정정은 그 연도 전체 내역에 반영한다. 사용자별 식사 원본이 아니라 표시용 연도 정보만 수정한다.
- 현재 학급 병기는 현재 운영 연도의 소속을 별도로 읽는다. 졸업·전출 등으로 현재 소속이 없으면 그 상태를 표시하며 과거 학급을 현재값으로 채우지 않는다.
- 표시용 연도 정보가 없으면 최신 학급으로 임의 대체하지 않고 `학년도 정보 확인 필요`로 표시한다.

### 8.2 이전 명부 삭제

- 이전 학년도 명부 전체 또는 선택 항목을 삭제할 수 있다. 삭제 전 Excel 다운로드와 대상 수를 보여준다.
- 실제 삭제 대상은 해당 `RosterEntry`다. 단순 숨김으로 바꾸었다고 설명하지 않는다.
- 해당 연도의 식사·체크인 표시용 `UserAcademicRecord`, `User`, 신청·확정일·체크인·사진·얼굴 연결은 삭제하지 않는다.
- 삭제 후 명부 메뉴에서 원래 명부를 다시 다운로드하는 기능은 제공하지 않는다. 식사 내역 다운로드에 필요한 당시 소속·이름은 계속 제공하며, 일반 명부로 자동 재생성하지 않는다.
- 이 기능은 모든 개인정보의 영구 삭제 기능이 아니다. 확인창에 “명부는 삭제되며, 식사 내역 표시용 학년도 정보와 식사 기록은 보존됩니다”라고 표시한다.
- 보존된 연도 정보 정정은 별도의 관리자 기록 정정 동작으로 허용한다. 명부 삭제 뒤에도 잘못된 과거 표기를 정정할 수 있다.

## 9. 권한·이메일·이용 종료

아래 세부 권한 경계는 이번 문서에서 제안하며 사용자 검토 후 확정한다.

- 메인 관리자는 현재 별도 관리자 로그인 계정으로 정의하고, 관리자·서브관리자 권한 부여·회수는 이 계정만 수행한다. 일반 명부 관리는 기존 읽기/쓰기 관리자 구분을 유지한다.
- 학년도 전환과 이전 명부 삭제도 메인 관리자에게 제한한다. 서브관리자는 조회·다운로드만 가능하다.
- 담임 배정은 학생 자료 접근 범위이므로 학년·반·번호·교사 업무는 관리자 명부 경로로만 수정한다. 교사 자기정보 화면에서 담임을 임의로 바꾸는 경로를 제거한다. 사진·얼굴 등록은 기존 개인 관리 흐름을 유지한다.
- 담당 학생 자료는 현재 운영 연도의 현재 담당반만 교사에게 제공하고, 이전 학년도 학급 자료는 관리자 조회로 제한하는 것을 제안한다. 재직 교사 자신의 과거 식사 내역 조회는 유지한다.
- 졸업·전출 학생과 전출·퇴직 교사는 로그인과 신규 이용을 막고 기록을 보존한다. 기존 관리자 권한 값은 자동 삭제하지 않되 계정 이용 중단이 우선하므로 관리자 API도 사용할 수 없다. 재활성화는 메인 관리자가 기존 권한을 확인한 뒤 명시적으로 처리한다.
- 이용 중단 계정이 Excel 또는 다음 연도 초안에 등장하면 확인 필요로 분류한다. 명부에 포함되었다는 이유만으로 재활성화하지 않으며, 별도 재활성화 확인 전에는 전환을 차단한다.
- 이메일 변경은 사용자 ID를 고정한 별도 동작으로 한다. 다른 계정의 이메일로 변경·병합할 수 없으며 변경 시 기존 세션을 무효화한다. 기존 파일의 이메일이 달라지면 다시 내려받도록 안내한다.
- 이메일 변경·이용 중단·권한 회수는 신규 로그인뿐 아니라 기존 JWT를 이용한 보호 API에서도 검사한다. 세션 버전과 최신 DB 상태를 서버 권한 판단에 사용한다.
- QR·얼굴 체크인도 최신 계정 상태와 해당 식사일 자격을 검증한다. 이름·학급 변경 때문에 사용자 ID·얼굴 임베딩·인쇄 QR을 다시 만들지 않는다.

## 10. 로컬 키오스크와 지연 동기화

- 학년도 전환 절차에 모든 운영 키오스크의 미전송 체크인 업로드, 잠시 사용 중지, 전환 후 명부·자격·얼굴 후보 재동기화, 운영 재개를 포함한다.
- 로컬 명부에는 운영 연도·명부 버전·계정 상태·식사일 기준 표시정보를 포함한다. 오늘 식사일이 다른 학년도에 속할 수 있으므로 운영 연도 숫자만으로 표시정보를 고르지 않는다.
- 로컬 데이터의 유효기간은 다음 KST 자정까지로 제한하는 것을 제안한다. 만료되면 동기화 전 신규 체크인을 막고, 이미 저장된 미전송 기록은 보존한다.
- 연결이 끊긴 장치에 서버의 차단·전환을 즉시 전달할 수 있다고 가정하지 않는다. 같은 날의 이용 중단도 장치 재동기화가 필요하다는 운영 안내를 제공한다.
- 최초 이용 상태의 확인 시점과 이후 상태 변경 시각을 기록한다. 서버가 발급한 동기화 버전에 해당 날짜의 자격 근거를 연결해 보존하고, 신청·공고의 자격 변경도 버전에 반영한다. 근거의 확인 시점 이전 상태를 임의로 소급 생성하지 않는다.
- 지연 업로드는 현재 졸업·전출 여부만으로 정상 과거 기록을 거부하지 않는다. 학생은 체크인 발생 시각의 이용 상태와 해당 날짜·식사의 APPROVED 확정 자격, 중복키를 검증한다. 교사 WORK/PERSONAL은 재직·이용 상태를 기준으로 하며 학생 식사 신청을 요구하지 않는다.
- 동기화 후 자격·이용 상태 변경으로 당시 판정을 입증할 수 없거나 필요한 근거가 없으면 관리자 확인 대상으로 보낸다. 현재 신청 상태를 당시 상태로 간주해 자동 반영하거나 정상 기록을 삭제하지 않는다.
- 이전 버전의 로컬 기록에 새 검증용 정보가 없으면 자동 폐기하지 않고 기존 호환 경로와 관리자 확인 대상으로 보존한다. 확정할 수 없는 항목은 거절 사유를 반환하고 로컬 미전송 기록에서 지우지 않는다.
- 모델·임베딩 차원·인식 임계값·얼굴 전처리·QR의 사용자 ID 체계는 변경하지 않는다.

## 11. 초기 데이터 이전과 운영 보호

### 11.1 검증 환경

운영과 분리된 시험용 PostgreSQL이 필요하다. 운영 백업을 복원해 이전과 검증을 수행한다. 앱은 우선 로컬에서 시험할 수 있으며, 실제 키오스크 통합 검증에는 별도 시험 배포를 사용할 수 있다. 새 운영 DB로 교체하는 것은 이 설계의 필수 조건이 아니다.

현재 Railway 서비스·브랜치·DB·Volume 연결은 미확인이다. 인프라 작업 전에 읽기 전용으로 확인하고, 시험 앱이 운영 DB나 업로드 Volume을 공유하지 않게 한다. 실제 서비스 생성·복원·운영 변경은 구체적인 실행 계획과 연결 대상을 검토한 뒤 수행한다.

### 11.2 추가 → 복사 → 검증 → 전환

1. 운영 원본의 복원 가능한 백업을 확보하고 별도 DB에서 복원 시험을 한다. 사진 파일 등 Volume 자료의 보존·복원은 DB 백업과 별도로 확인한다.
2. 사전 조사에서 사용자 ID·이메일 충돌·중복 학번·필수값 누락·공고 대상기간·확정일·체크인 날짜를 확인한다. 비밀값과 학생 명단을 로그에 출력하지 않는다.
3. 새 테이블과 호환 가능한 nullable 참조를 추가한다. 초기 변경에서 기존 컬럼 삭제·이름 변경·사용자 재생성·식사 행 재작성은 하지 않는다.
4. 현재 사용자 정보를 2026학년도 명부와 표시용 기록에 복사하고 기존 공고를 연결한다. 2026학년도 범위 밖 날짜 또는 모호한 데이터가 있으면 자동 재분류·삭제하지 않고 예외로 보고한다. 귀속이 모호한 예외는 관리자의 결정과 재검증이 끝날 때까지 새 기능 전환을 차단한다.
5. 기존 결측값은 임의로 채우지 않는다. 현재 운영을 깨뜨리지 않게 원본 상태를 복사하고 보완 대상으로 표시한다. 새로운 가져오기와 새 학년도 전환에서는 필수 검증을 적용한다.
6. 이전 완료 전 재실행은 누락된 초기 정보만 보완한다. 이미 수정된 연도 기록을 현재 `User` 값으로 덮어쓰지 않도록 이전 완료 상태와 기준 버전을 검사한다. 초기 이전 완료 후의 명부 부재는 백필 누락으로 취급하지 않으며, 관리자가 삭제한 `RosterEntry`를 재생성하지 않는다.
7. 사용자 ID와 원본 테이블별 ID·전체 필드 값·참조·건수를 비교한다. 신청 상태·서명·식사별 선택·확정 날짜·체크인 시각·얼굴 등록·사진 경로도 보존 여부를 검증한다. 건수만 같은 것을 보존 성공으로 판정하지 않는다.
8. 모든 관련 조회·쓰기 경로가 연도 정보를 사용하도록 바꾼 뒤 새 관리 기능을 연다. 과거 코드가 `User`만 수정하는 상태로 신·구 앱을 동시에 운영하지 않는다.
9. 운영 반영은 짧은 쓰기 중단 구간과 새 백업을 확보한 상태에서 수행해 검증 기준 시점이 흔들리지 않게 한다. migration을 포함한 배포 시작 명령도 실행 순서에 포함한다.
10. 실패 시 원본을 자동 복원해 새 데이터를 덮어쓰지 않는다. 추가 스키마를 남기고 이전 완료 상태에 맞는 호환 앱으로 운영할 수 있는지 먼저 판단한다. 새 기능 사용 이후 무조건 옛 앱으로 되돌리는 방식은 허용하지 않는다.

### 11.3 운영 적용 전 필수 검증

| 분류 | 확인할 결과 |
|---|---|
| 최초 이전 | 모든 기존 사용자 ID·식사 원본·관계가 동일하고 2026학년도 연결이 완전함 |
| 반복 실행 | 초기 이전·Excel 확정·전환 재시도에서 중복과 덮어쓰기 없음 |
| 학년도 | 2월 말/3월 1일, 윤년, KST 경계 및 1·2월 귀속 정확 |
| 초안 | 신규·기존 사용자 모두 전환 전 현재 계정·표시·접수에 영향 없음 |
| Excel | 두 시트, 빈 시트, 부분/전체 범위, 중복, 수식, 오류, 오래된 파일, 이메일 변경, 동시 수정 |
| 전환 | 누락자 확인 없이는 차단, 중간 실패 시 전체 취소, 완료 후에만 새 연도 접수 |
| 과거 기록 | 진급 후 옛 내역이 옛 연도 최종 학급으로 표시되고 명부 삭제 후에도 동일 |
| 권한 | 과거 JWT·QR로 종료된 계정 이용 불가, 교사 직접 담임 변경 불가, 권한 부여 경계 준수 |
| 신청 | 과거 공고 재계산과 신청 Excel이 현재 학년으로 잘못 처리하지 않음 |
| 키오스크 | 새 명부 동기화, 로컬 만료, 전환 전 미전송 기록, 종료 전 정상 기록의 지연 업로드 보존 |
| 회귀 | 기존 식사 신청·교사 체크인·QR·얼굴 확인·다운로드 동작 유지 |

구현 단계에서는 관련 단위·DB 통합 테스트, 브라우저 확인, lint·타입 검사·build를 수행한다. 실제 백업 복원과 운영 전후 비교는 앱 테스트와 구분하여 기록한다.

## 12. 변경 범위와 구현 단위

기존 ExcelJS, `EditableCell`, 권한 유틸, 날짜/KST 유틸, Prisma 공용 인스턴스, 식사 확정일 판정을 재사용한다. 관리자 페이지 전체를 무관하게 재작성하지 않고 명부·가져오기·전환 UI만 분리한다.

| 단위 | 주요 책임·관련 경로 |
|---|---|
| 학년도 도메인 | 새 연도 모델·KST 귀속·활성 연도·표시 정보 조회, `prisma/schema.prisma`, `src/lib/date-range.ts`, `src/lib/timezone.ts` |
| 명부 관리 | 새 명부 서비스, `src/app/api/admin/users/route.ts`, 기존 셀 편집의 연도 지정 |
| Excel | 새 양식·파서·미리보기·확정 API. 기존 `/api/admin/import`의 Sheet 쓰기 종료 |
| 학년도 전환 | 누락자·초안 버전·원자적 활성화·작업 기록 |
| 화면 | `src/app/admin/page.tsx`와 새 명부 전용 UI. 기존 학생·교사 표 재사용 |
| 인증·개인정보 | `src/auth.ts`, `src/lib/permissions.ts`, `src/proxy.ts`, `src/app/api/users/me/route.ts`, 보호 API 및 QR·얼굴 상태 검사 |
| 식사·통계 | `src/lib/meal-plan-server.ts`, 관리자/담임 조회·공고/신청 import/export·본인 이력 |
| 로컬 동기화 | `src/lib/kiosk-sync.ts`, `src/lib/local-db.ts`, QR/얼굴 로컬 판정, `src/app/api/sync/*` |
| 초기 이전 | 추가형 migration, 재실행 가능한 2026 backfill, 원본 비교 검증 |

구현 계획은 이 책임 순서에 맞춰 검증 가능한 작업으로 나누되, 운영 기능 공개는 전체 연도 일관성이 확보된 뒤 진행한다. 스키마/마이그레이션, UI, 구조 맵, 배포 환경은 프로젝트에 지정된 검토 역할을 사용한다.

## 13. 이번 설계에서 새로 제안하는 세부 정책

다음은 앞선 질문에서 개별 확정받은 사항과 구분한다. 이 문서 검토 시 함께 확인받는다.

1. Excel의 일부 수정/전체 대조 구분, 오류 시 전체 미반영, 버전 충돌 차단.
2. 전출·퇴직 교사도 누락 확인과 이용 중단 대상으로 관리.
3. 학년도 전환·이전 명부 삭제·권한 지정은 메인 관리자만 가능.
4. 교사 업무의 본인 직접 수정 종료, 과거 학급 자료는 관리자 조회, 본인 식사 이력은 유지.
5. 새 공고의 학년도 경계 초과는 공고 분리로 처리.
6. 로컬 명부는 다음 KST 자정까지 유효하며, 전환 후 재동기화 없이 운영 재개하지 않음.
7. 이전 명부를 실제 삭제해도 연도별 내역 표시정보는 남고, 그 명부의 일반 다운로드는 종료.

## 14. 다음 단계와 현재 검증 상태

- 설계 문서의 요구사항 대응·모순·경로·삭제 경계·이전 절차를 검토한다.
- 사용자가 이 문서를 검토한 뒤 구현 계획을 작성한다. 계획 검토 후 구현한다.
- 이번 문서 작성에서 앱 코드 수정, Prisma 명령, DB 접속·복원, Railway 변경, 앱 테스트·빌드는 실행하지 않았다.
- 문서가 검토됐다는 사실을 실제 migration SQL 안전성 승인이나 운영 데이터 보존 검증으로 대체하지 않는다.
